# مخطط إعادة تصميم نظام الشكاوى — النسخة الأولى

> **حالة المستند:** مقترح معماري وتجربة مستخدم قابل للمراجعة. لا يغيّر تصميم الشاشات أو قاعدة البيانات أو صلاحيات الإنتاج حتى يُعتمد التنفيذ. **المرجع:** main عند `19f55a01075932bd09d404fb69d4171fb43b84df`.

## 1. الهدف ونطاق الإصدار

إعادة بناء **هيكل التنقل وتجربة معالجة الشكوى** في التطبيق المحلي (Windows / Electron) بحيث يحقق:

- وصولاً سريعاً إلى تسجيل بلاغ أو استفسار وتحديد حالته ومسؤوله.
- شاشة متابعة تبيّن الأعمال المطلوبة اليوم، ونواقص البيانات، والتأخير، والاعتمادات.
- تفاصيل شكوى كاملة قابلة للعمل بدلاً من تجميع جميع الإجراءات في نوافذ صغيرة.
- هوية مؤسسية عربية RTL باسم «شعبة الاستفسارات والشكاوى»، مع Thmanyah Sans مثبت محلياً، ولوحة ألوان خضراء رسمية ولمسات ذهبية محدودة.
- المحافظة على إدارة الحسابات وسجل التدقيق والمرفقات والنسخ الاحتياطي والصلاحيات الموجودة فعلاً.

**خارج النطاق في أول دفعة:** تبديل قاعدة البيانات، إتاحة الخادم عبر الإنترنت، التكامل التلقائي مع واتساب/تلغرام، وإعادة كتابة منطق الحالات أو الصلاحيات.

## 2. ما يوجد حالياً (مراجع ملفات)

| عنصر | حالة الكود الحالية | أثره |
| --- | --- | --- |
| `index.html` | شريط جانبي بسبع وجهات: dashboard, complaints, referrals, replies, notifications, reports, settings | جميع أقسام العمل في مستوى واحد دون تقسيم حسب الدور أو المهمة |
| `app.full.js` | `render()` يختار الدالة حسب مفتاح الصفحة و`go()` يبدل الوجهة في المحتوى | منصة واجهة أحادية الملف (~83 ألف حرف) يصعب تغييرها واختبار كل شاشة بمعزل عن الأخرى |
| `styles.css` + `ui-enhancements.css` | أشكال ومكونات وتعديلات محلية | توجد ازدواجية في قواعد الأنماط |
| `modules/*` | خدمات ومسارات Express منفصلة للمصادقة والشكاوى والمرفقات والتقارير ... | يجب **إعادة استخدامها** لا نسخها |
| `app_state` + جدول `complaints` | بيانات شكاوى داخل JSON مع مرآة في SQLite | يجب تجنّب تغيير التخزين ضمن إعادة تصميم الواجهة |
| `desktop/main.js` | تطبيق Electron محلي `127.0.0.1` | يحافظ التصميم الجديد على التشغيل المحلي ومحدودية إتاحته |

## 3. خريطة التنقل المقترحة

### شريط علوي ثابت

- هوية الجهة وعنوان الشاشة + مسار تنقل Breadcrumbs.
- زر رئيسي دائم: **«+ تسجيل شكوى / استفسار»** (يظهر لمن يملك `complaints.create`).
- بحث سريع برقم الشكوى أو اسم صاحب العلاقة، مرتبط بصلاحية الاطلاع.
- إشعارات ذات أولوية، قائمة الحساب، وإعدادات العرض.

### قائمة جانبية منظمة حسب مسارات العمل

**مكتب الشعبة**
1. لوحة العمل — إحصاءات عملية وقائمة أولويات اليوم.
2. الوارد الجديد — شكاوى واستفسارات جديدة، ومسودات.
3. مهامي — ما أسند إلى المستخدم، ويحتاج إجراء الآن.

**المعالجة**
4. سجل الشكاوى — سجل شامل مع تبويبات سريعة حسب الحالة، المحافظة، الجهة والتاريخ.
5. استكمال البيانات — سجلات ناقصة وموعد المتابعة التالي.
6. الإحالات والمتابعة — قائمة الجهات والإحالات وما تنتظر عليه ردوداً.
7. الردود والاعتمادات — ردود معدة، بانتظار المراجعة، معتمدة أو مرسلة، بإجراءات مختلفة حسب الصلاحية.

**الرقابة**
8. التنبيهات والتأخيرات — فوات SLA، أولويات عاجلة، إشعارات.
9. التقارير — مقارنة المحافظات والجهات، وتصدير CSV/XLSX/PDF ضمن الصلاحيات.
10. سجل التدقيق — للمدير/المراجع المصرح به فقط.

**الإدارة** (للمخولين فقط)
11. المستخدمون والصلاحيات.
12. القوائم والإعدادات — المحافظات، الجهات، التصنيفات، القوالب، مدة المتابعة.
13. النسخ الاحتياطي والمزامنة اليدوية وإجراءات التشغيل.

> بعض الوجهات الجديدة هي **عروض مصفّاة للبيانات الموجودة** ولا تعني إنشاء جداول أو مسارات API جديدة في البداية. يخفي شريط التنقل العناصر التي لا يملك المستخدم صلاحيتها، لكن **التحقق النهائي يبقى إلزامياً على الخادم**.

## 4. الشاشات الأساسية

### لوحة العمل
- صف مؤشرات: وارد اليوم، مفتوح، متأخر، يحتاج استكمال، بانتظار اعتماد.
- قائمة «تحتاج تدخلك» مرتبة بالتأخير ثم الأهمية، مع إجراء واحد واضح لكل صف.
- بطاقة موجزة لتوزيع الحالات والمحافظات؛ لا نحتاج رسومًا كثيرة تقلل سرعة العمل.
- لا تعرض بيانات حساسة قبل تسجيل الدخول أو دون صلاحية.

### سجل الشكاوى
- بحث/فلاتر متقدمة قابلة للإلغاء (حالة، محافظة، موقع/جهة، فئة، تاريخ، مسؤول).
- أعمدة افتراضية: رقم، الموضوع، المحافظة، الحالة، المسؤول، الأولوية، مدة البقاء، آخر تحديث.
- تحديد صف ثم فتح **صفحة تفاصيل مستقلة**؛ الإشعارات السريعة والحذف ليستا واجهة التعديل الرئيسية.
- عدادات خاصة للمسودات والناقص والمتأخر.

### تسجيل شكوى أو استفسار
نموذج موجه بأقسام واضحة:
1. نوع الطلب (شكوى/استفسار)، المصدر (هاتف/واتساب/يدوي)، المحافظة والموقع/الجهة.
2. بيانات صاحب الطلب؛ حقول التعريف غير المطلوبة لا تجعل الحفظ مستحيلاً.
3. موضوع الطلب ووصفه وتصنيفه وأولويته.
4. المسؤول والمرفقات وملاحظات الموظف.
5. مراجعة موجزة ثم حفظ؛ رقم رسمي يُنشأ عند أول حفظ بواسطة الخادم.

### تفاصيل الشكوى: محور النظام
- رأس ثابت: الرقم، الحالة، الأولوية، المسؤول، العمر الزمني وأزرار الإجراءات المخولة.
- محتوى بتبويبات: **الملخص | التسلسل الزمني | الإحالات | المراسلات والردود | المرفقات | سجل التدقيق**.
- انتقالات الحالة مرتبطة بقواعد الخادم وسبب الإغلاق/الإلغاء.
- الاعتماد من مستخدم مخوّل آخر عند لزومه، مع إبقاء مسودة الرد ثابتة قبل الاعتماد.
- حقول الاتصال والمرفقات لا تُنشر في روابط عامة.

### التقارير والإدارة
- صفحة تقارير كاملة مع فلترة وإحصاءات وتصدير موثق.
- صفحات إدارة منفصلة للمستخدمين والصلاحيات والإعدادات والنسخ الاحتياطي؛ واجهات الإدارة لا تظهر لمستخدم غير مخوّل.

## 5. اتجاه التصميم المرئي

- **RTL حقيقي** في شريط التنقل والجداول والحقول والنوافذ.
- اللون الأساسي أخضر داكن رسمي، أسطح بيضاء/رمادية، ذهبي محدود للتأكيد.
- حالة التأخير **بلون ونص وأيقونة** لا باللون فقط؛ مقروءة لضعف التمييز اللوني.
- عناوين واضحة، جداول ذات كثافة عملية، أزرار لمس لا تقل عن 40–44px.
- وزن خط ثمانية 400/500/700 مع احتياطي Tahoma/Segoe UI؛ لا توزيع لملف الخط الخام.
- دعم لوحة المفاتيح، التنقل داخل الحوارات، وإرجاع التركيز للمصدر بعد إغلاقها.

## 6. هيكل الواجهة البرمجي المستهدف

```text
src/
  app/
    bootstrap.js              # بدء الجلسة وتهيئة التطبيق
    navigation.js             # المسارات، عناوينها، وصلاحيات عرضها
    router.js                 # تنقل وتاريخ المتصفح
    api-client.js             # fetch وCSRF ومعالجة أخطاء HTTP
    state.js                  # بيانات شاشة مؤقتة، لا نسخة محلية بديلة عن الخادم
  components/
    app-shell.js              # الشريط العلوي والجانبي
    page-header.js
    data-table.js
    filters.js
    form-controls.js
    modal.js
    status-badge.js
  features/
    dashboard/
    intake/
    complaints/
    follow-ups/
    referrals/
    replies/
    notifications/
    reports/
    administration/
  styles/
    tokens.css
    layout.css
    components.css
    utilities.css
public/
  index.html
  assets/
```

نوصي بأداة بناء محدودة مثل esbuild لإخراج ملفات ثابتة من `src/` إلى `public/`، وبإبقاء `modules/*` و`config/*` على حالها أثناء انتقال الواجهة. يجب أن يقدم Express ملفات `public/` فقط وألا يُكشف `src/` أو `data/`.

الانتقال تدريجي: نقل مكونات عامة أولاً، ثم لوحة العمل، ثم السجل والتفاصيل، ثم بقية الصفحات؛ لا يُحذف `app.full.js` قبل إثبات التطابق والوظائف وإعادة الاختبار.

## 7. خطة تنفيذ آمنة

| الدفعة | نطاق التغيير | معيار القبول |
| --- | --- | --- |
| A | نظام تصميم + AppShell + شريط تنقل من بيانات موحدة | كل الوجهات الحالية تعمل، لا تغيير API |
| B | لوحة عمل، سجل، صفحة تفاصيل الشكوى | إنشاء/حفظ/بحث/مرفقات وحالات دون فقد |
| C | الإحالات، الردود، الاعتمادات، الاستكمال والتذكيرات | صلاحيات فعلية، اعتماد من مستخدم مختلف، أحداث تدقيق |
| D | التقارير والإدارة وتحسينات الاستجابة | تطابق نتائج التقارير وظهور الواجهات المصرح بها |
| E | استخراج الوحدات ودمج CSS والتخلص من بقايا الشرائح | CI + بناء Windows + قبول يدوي على Windows |

### اختبارات إلزامية قبل الدمج

1. حفظ شكوى عبر API ثم ظهورها بعد إعادة فتح التطبيق.
2. نجاح حالات الإغلاق/إعادة الفتح فقط وفق السياسات المعتمدة.
3. عدم وصول موظف غير مخوّل إلى إدارة المستخدمين أو الاعتمادات.
4. اختبار تعارض `X-State-Revision` وعدم ضياع تعديل موظف آخر.
5. رفع/تنزيل مرفق والنسخ الاحتياطي واستعادته دون فقد.
6. شاشة عربية عند عرض 1366×768، و1024×768، وحجم شاشة صغير دون تداخل.
7. اختبارات لوحة مفاتيح، العناوين، الملصقات، التباين، ورسائل الأخطاء.
8. تشغيل Windows EXE من بناء ناجح مع حفظ بيانات SQLite خارج مجلد التطبيق.

## 8. ضوابط مهمة

- لا مساس ببيانات حية أو `main` قبل مراجعة التصميم، واختبار فرع الواجهة.
- لا تغيير للسياسات الإدارية (صلاحيات الاعتماد، حذف السجلات، المجهولية) بناء على التصميم المرئي وحده.
- لا تفعيل تلقائي لاتصال إنترنت أو لوحة مواطن عامة.
- الهدف الأول **تقليل نقرات إنجاز الشكوى وتمييز المهام العاجلة**، ثم تحسين الشكل والتفاصيل.
