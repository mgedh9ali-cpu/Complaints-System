# قائمة القبول اليدوي قبل الاستخدام الفعلي

هذه القائمة مخصصة للتنفيذ على أجهزة Windows الفعلية. نجاح GitHub Actions لا يحل محلها. استخدم بيانات وهمية فقط، ولا تدخل بيانات مواطنين حقيقية خلال الاختبار.

## 1. التشغيل المحلي دون إنترنت

- [ ] جهّز Node.js والاعتماديات على الجهاز قبل فصله عن الإنترنت.
- [ ] افصل Wi-Fi وEthernet فعليًا، ثم شغّل `start-windows.bat`.
- [ ] افتح `http://127.0.0.1:3000` وسجّل الدخول بالحساب المحلي.
- [ ] أنشئ شكوى اختبار، ثم عدّل حالتها، وسجّل الخروج والدخول مجددًا؛ يجب أن تبقى البيانات محفوظة.
- [ ] في PowerShell نفّذ: `Get-NetTCPConnection -State Listen -LocalPort 3000 | Select-Object LocalAddress,LocalPort,OwningProcess`.
- [ ] تحقّق أن عنوان الاستماع هو `127.0.0.1` فقط، وليس `0.0.0.0` أو عنوان شبكة الجهاز.
- [ ] أعد تشغيل التطبيق مع بقاء الإنترنت مفصولًا وتأكد من استمرار الوظائف المحلية.
- [ ] سجّل إصدار Node.js، وإصدار التطبيق، ونتيجة كل خطوة وتاريخها.

**معيار النجاح:** تعمل وظائف الدخول وحفظ الشكاوى محليًا مع انقطاع الإنترنت، ولا يستمع الخادم إلى واجهة الشبكة المحلية. هذا لا يثبت وحده انعدام كل حركة الشبكة الصادرة؛ يجب إجراء مراجعة منفصلة لقواعد جدار الحماية وبيئة التشغيل.

## 2. اختبار المزامنة اليدوية بين جهازين

- [ ] جهّز الجهازين بالإصدار نفسه والاعتماديات نفسها، وافصل الإنترنت عنهما.
- [ ] أنشئ على الجهاز A شكاوى وهمية ذات معرّفات وحالات معروفة.
- [ ] صدّر ملف المزامنة وانقله بوسيط تخزين معتمد؛ لا تستخدم بريدًا أو خدمة سحابية.
- [ ] على الجهاز B، أنشئ نسخة احتياطية من قاعدة بياناته قبل الاستيراد.
- [ ] استورد الملف بصلاحية المدير، وتحقق من عدد الشكاوى ومعرّفاتها وحالاتها.
- [ ] تحقق أن استيراد البيانات لم يشغّل ملفات برنامج مستوردة تلقائيًا.
- [ ] اختبر ملفًا تالفًا أو معدّلًا على قاعدة اختبار منفصلة، وتأكد من رفضه دون إفساد البيانات الحالية.
- [ ] سجّل نتيجة التعارض بوضوح: الاستيراد يستبدل حالة البيانات ولا يدمج التعديلات المتعارضة تلقائيًا.

**معيار النجاح:** انتقال البيانات عبر ملف يدوي فقط، مع بقاء الجهازين مستقلين، ونجاح التحقق من سلامة الحزمة ورفض الحزمة التالفة.

## 3. اختبار النسخ الاحتياطي والاستعادة الفعلية

- [ ] أوقف الخادم قبل النسخ الثابت المعتاد، أو استخدم إجراء النسخ المتسق المعتمد.
- [ ] أنشئ نسخة احتياطية جديدة باستخدام `node scripts/backup-database.js ./backups/acceptance-test.sqlite` بعد التأكد من عدم وجود الملف مسبقًا.
- [ ] شغّل `node scripts/verify-database-restore.js ./backups/acceptance-test.sqlite`.
- [ ] انسخ النسخة إلى مسار اختبار منفصل، ولا تستبدل قاعدة البيانات الأصلية.
- [ ] شغّل نسخة التطبيق على قاعدة الاختبار، وتحقق من الدخول، وقراءة الشكاوى، وإنشاء شكوى وهمية وتغيير حالتها.
- [ ] أوقف نسخة الاختبار، ثم تحقق من سلامة قاعدة الاختبار وسجل التدقيق إن كانت سلسلة التدقيق مثبتة في الإصدار.
- [ ] وثّق الزمن اللازم للاستعادة وأي فقد بيانات أو خطأ ظهر.

**معيار النجاح:** استعادة قاعدة منفصلة وتشغيل التطبيق عليها فعليًا، لا مجرد نجاح فحص SQLite أو مقارنة أعداد الصفوف.

## 4. سلامة سجل التدقيق

بعد دمج ميزة سلسلة البصمات في الإصدار الذي يجري اختباره:

- [ ] نفّذ `node scripts/verify-audit-log.js` وتأكد من نجاح التحقق.
- [ ] على نسخة قاعدة بيانات اختبار فقط، غيّر حدثًا أو احذف حدثًا ثم أعد الفحص؛ يجب أن يفشل التحقق.
- [ ] اختبر أن المراجع لا يستطيع تغيير حالة الشكوى، وأن المدير/الموظف المخوّل يستطيع ذلك.
- [ ] احتفظ بنتائج الفحص خارج مجلد قاعدة البيانات.

**حد معروف:** سلسلة SHA-256 تكشف العبث ما لم يُعِد المهاجم بناء السلسلة كاملة. لا تُعد سجلًا غير قابل للتلاعب أمام شخص يملك ملف قاعدة البيانات؛ يلزم تثبيت نقطة تحقق خارج الجهاز أو جهة تدقيق منفصلة لضمان أقوى.

## 5. قرار القبول

- [ ] جميع الاختبارات الآلية ناجحة على commit الإصدار المراد نشره.
- [ ] جميع خطوات الأقسام 1–4 موثقة بنتائج فعلية على الجهازين.
- [ ] نسخة احتياطية معتمدة محفوظة على وسيط مصرح به ومحمي.
- [ ] مراجعة مستقلة لسياسات الوصول والاحتفاظ والسرية تمت قبل استخدام بيانات حقيقية.
- [ ] تحديد ما إذا كان مشغّل `start-windows.bat` كافيًا؛ فهو ليس مُثبّت Windows مستقلًا بصيغة EXE.

لا توضع علامة «جاهز 100%» إذا بقي أي مربع غير مكتمل. توقيع المسؤول عن الاختبار وتاريخ التنفيذ مطلوبان في سجل القبول الداخلي.
